EXECUTION NOTES — Product Rescue Mission pipeline run
======================================================
Running log of problems hit while actually executing the pipeline on this
machine (not just writing the code), and what was done about each one.
Updated as the run progresses.

ENVIRONMENT
-----------
- No Python was installed on this machine at all. Installed Python 3.12.10
  via `winget install Python.Python.3.12`, then created a venv in
  .venv/ and installed requirements.txt into it (~5-10 min, ~2GB of

BUGS FOUND ONLY BY RUNNING THE CODE (not visible from reading it)
-------------------------------------------------------------------
1. setup_scripts/stream_data.py — load_dataset() call was missing the
   dataset repo ID. Constants were refactored to CATEGORY_CONFIG /
   META_CONFIG but the actual `load_dataset(CATEGORY_CONFIG, ...)` calls
   only passed the config name as the first positional arg, which
   HuggingFace's `datasets` interprets as the repo path — so it looked
   for a dataset literally named "raw_review_Electronics" and failed
   with DatasetNotFoundError. Fix: added DATASET_REPO =
   "McAuley-Lab/Amazon-Reviews-2023" and passed both
   (DATASET_REPO, CATEGORY_CONFIG) positionally. This is exactly the
   kind of bug that only shows up at actual execution time — static
   review missed it.

2. xgboost's `use_label_encoder=False` param (already removed in the
   earlier code-review pass, before this run) — confirmed xgboost 2.1.3
   installs and trains cleanly without it.

DIFFICULTIES / SLOW STEPS AND HOW THEY WERE ADDRESSED
--------------------------------------------------------
1. Metadata (brand/category) lookup pass was the single biggest time
   sink. The Electronics metadata config has no ordering relationship to
   review-count popularity, so finding a specific ~50 target ASINs in it
   meant scanning a large, effectively random fraction of ~1.6M records.
   Measured throughput: ~1,000-1,200 rows/sec with frequent HTTP read
   timeouts, vs ~6,000 rows/sec on the review stream. A first attempt
   with a 2,000,000-row cap ran for over 80 minutes and still hadn't
   finished (stalled hard around 15-21% multiple times).
   FIX: made the metadata pass optional and OFF by default
   (PRM_FETCH_META=1 to opt in), and stopped depending on it for
   anything functional. Product type (used to pick same-type
   competitors) is now derived straight from review text instead — see
   #3 below. Brand name is still nice-to-have display info from
   metadata when enabled, but nothing breaks without it.

2. Three separate streaming passes over the review data (count, then a
   second full pass to collect rows for the winners) doubled network
   exposure on an already-flaky connection.
   FIX: merged counting and row-collection into ONE pass. Insight: total
   buffered memory is bounded by MAX_SCAN regardless of how rows are
   distributed across ASINs (buffering unevenly costs no more than
   buffering evenly — the total can never exceed rows scanned), so there
   was no memory reason to defer collection to a second pass. This cut
   review-stream network passes from 2 down to 1.

3. First product-type detection attempt only checked the FIRST review
   seen for a given ASIN, extracting a keyword like "earbuds" or
   "charger" from its title+text. This produced a wrong result on the
   real data: the flagship's type was detected as "charger" when the
   product is actually Bluetooth headphones/earbuds — one early review
   happened to mention "charger" incidentally (e.g. complaining about
   charging) before any review mentioning "headphones" was seen, and the
   first-hit-wins logic locked that in permanently.
   FIX: switched to a majority vote across every buffered review for a
   candidate ASIN (only needed for the ~50 top candidates, done AFTER
   the streaming pass from data already in memory — no extra network
   cost). Verified against the real data: correctly resolved to
   "headphone" this time, and competitor selection produced sensible
   type-matched candidates.

4. The HuggingFace connection from this machine has been unreliable
   throughout — intermittent multi-minute read timeouts against both
   huggingface.co and its AWS CDN edge (us.aws.cdn.hf.co), sometimes
   recovering in seconds, once stalling for over an hour before a
   backlog cleared. This is an external network condition, not
   something fixable in our code. Two things helped:
     - Fewer passes (see #2) means less total exposure to a bad
       connection.
     - Installed `hf_xet` (added to requirements.txt) for the model
       downloads (RoBERTa, translation model, etc.) — HuggingFace's Xet
       storage backend does chunked, deduplicated, resumable transfer
       instead of a single large HTTP GET, which is much more tolerant
       of a flaky connection. Day 1's ~1.1GB RoBERTa model failed
       repeatedly on the plain-HTTP path before hf_xet was installed,
       then downloaded cleanly right after.
   There is no code-side fix for the network itself — if a run stalls
   for a very long time with no progress, the right move is to check
   `Get-Process python` for CPU usage (confirms it's actually working
   vs. truly stuck) rather than assume it's broken.

5. Day 4's XGBoost churn classifier scored a suspicious AUROC / F1 /
   Precision / Recall of 1.0000 with a PERFECT confusion matrix
   ([[821,0],[0,82]]) on the first real run. That is not a good model —
   it is a red flag for data leakage. Root cause: `is_silent_killer`
   (the target) is DEFINED in day1_roberta_sentiment.py as a formula
   built directly from star_rating, prob_negative, and prob_positive —
   and all three of those (plus star_normalized and star_gap, which are
   deterministic functions of them) were also in the classifier's
   FEATURES list. The model wasn't predicting anything; it was just
   re-deriving the exact rule that generated its own label — a
   tautology dressed up as a classifier. This would have been an
   embarrassing thing to present to judges as "98%+ accurate churn
   prediction."
   FIX: removed star_rating, star_normalized, star_gap, prob_negative,
   prob_neutral, prob_positive from FEATURES entirely. Left:
   helpful_votes, verified_purchase, emo_anger, emo_sadness, emo_joy,
   review_length — signals that don't tautologically encode the label,
   and which fit the actual "Silent Killer" premise (frustration
   visible somewhere OTHER than stars/sentiment). Re-ran: AUROC dropped
   to a realistic 0.8015 (5-fold CV: 0.7805 +/- 0.0169), F1 0.3482,
   precision 0.2746, recall 0.4756 — a genuine, presentable, honestly-
   earned result instead of a leaked one. Top features by importance
   are now emo_joy, emo_sadness, review_length — exactly the kind of
   "hidden signal" story this project is supposed to be telling.
   This is the single most important thing this execution pass caught:
   it was invisible from reading the code (the leak is a cross-file
   relationship between how day1 builds the label and how day4 builds
   its feature list) and only surfaced because the metrics were
   actually inspected after a real run, not assumed correct because the
   script exited 0.

Bugs found (again, only by running it):
1. day3.6's `build_corpus()` sorted candidate reviews longest-first and
   `break`-ed the moment one review didn't fit the char budget. Since
   the single longest review for "Sound Quality" (3,038 chars) exceeded
   the 3,000-char budget on its own, and was tried FIRST, the loop broke
   immediately and returned an empty corpus — silently producing no
   summary for the aspect with the MOST complaints (519), and same root
   cause zeroed out the "overall" summary too. Fixed: skip oversized
   items instead of breaking, and if literally every candidate is too
   long, truncate the shortest one rather than give up. Also switched
   from "N longest reviews" to a length-filtered random sample (min 20
   words) so the summary reflects the complaint set broadly instead of
   being dominated by one or two verbose outliers.
2. day3.7's brand-guessing heuristic first tried "most frequent
   capitalized word" and confidently returned "Sound", "Very", "Love" —
   sentence-initial capitalization, not brand names. Fixed by only
   counting a capitalized word when it appears mid-sentence (not
   preceded by `. `, `! `, `? `, or start-of-string) — genuine proper
   nouns get capitalized mid-sentence too ("I love my Senso earbuds"),
   generic words basically only get capitalized by starting a sentence.
   After the fix: correctly resolved Senso (flagship), Panasonic and
   Edifier (2 of 3 competitors — real, known audio brands). The 3rd
   competitor's top candidates ("Siri", "Airpods") were just under the
   2%-of-reviews confidence threshold and were, on inspection, genuine
   competitor-comparison references ("I've bought knock off earbuds...
   caved and decided to buy the Apple product") rather than the
   product's own brand — left as "Unknown" rather than guessing wrong.
3. Two NaN/placeholder inconsistencies: pandas round-trips an empty CSV
   string back as NaN (float) on reload, which crashed an f-string
   slice (`'float' object is not subscriptable`); separately, the
   flagship's "no title" placeholder was `""` but the competitors' was
   the literal string `"Unknown"` — an inconsistency that made `title =
   official_title or guess_product_type(...)` silently keep "Unknown"
   instead of falling through to the guess. Normalized both NaN and the
   literal string "Unknown" to the same empty-string handling.
